# Writing Style — Raymond Chu

## Tone
Professional, direct, senior. No fluff. JD keywords only when genuinely
applicable. Reframe real experience, never fabricate.

## Sentence Style
- No em dashes.
- No long run-on sentences. A sentence chaining 2-3 ideas together with
  commas and "and"/"then" is a run-on even if grammatically legal. A
  colon or semicolon does not exempt it — "X does Y; Z does W, which
  means..." is the same violation wearing different punctuation.
- One idea per sentence. Short, direct, complete sentences.

### Mandatory pre-presentation scan
Before showing any drafted or revised prose to the user — a cover letter
paragraph, an application-form answer, a profile statement — re-read every
sentence against the run-on rule above. Do this on every revision, not
just the first draft: a fix applied to one sentence (e.g. splitting a
run-on) routinely introduces a new one in the sentence next to it, and
that new violation is exactly as visible to the user as the one just
fixed.

## Bullet Structure
- Lead with result/accomplishment, not duty.
- Every Skills-line item must be backed by at least one KB-confirmed story
  that would hold up under a follow-up interview question. If the honest
  answer is "one modest story" or "proposal stage only," soften the word
  choice or flag the thinness explicitly.

## Metrics Discipline
- Baseline metrics are a floor, not a ceiling. Cite as-is, never round up
  or embellish beyond what's labeled [CONFIRMED].
- Never state a [MISSING] metric as if it were confirmed.
- [EST] and [CALCULATED] metrics may be used but should be flagged as such
  if precision matters to the context.

## Honesty & Gap Handling
- "Not documented yet" is not the same as "doesn't exist." Check for
  adjacent/partnered experience before assuming a clean gap.
- If a genuine gap exists, leave it off the resume entirely. Never write
  "no experience with X" or a hedge on outward-facing content. Gaps get
  discussed directly, never surfaced on the page itself.
- Never assume a scope, seniority, or employment-structure correction
  independently — confirm before applying.

### Analogy accuracy (distinct from factual accuracy)
Every individual fact in a comparison can be true and the comparison
itself can still be false. When drawing a parallel between the
candidate's past work and the target company's product or problem,
check the comparison at the mechanism level, not just the surface level.
"Automates a manual process" and "computes/infers a new value from
data" are different mechanisms even when both get described as
"automation" — a tool that speeds up entering an already-known number is
not the same claim as a tool that calculates an unknown one. Before
presenting an analogy, ask: does the underlying *how* actually match, or
only the *shape* of the story? If only the shape matches, say so
explicitly ("adjacent, not identical") rather than letting the analogy
imply equivalence it can't back up under a follow-up question.

## Cover Letters
- Line 1: punchy anchor, no "I am writing to apply."
- Body: 2-3 short paragraphs, strongest stories mapped to JD requirements.
- Clean, confident close.
- Same no-em-dash, no-run-on rules apply.

## Application Q&A (short-answer portal questions)
- 2-4 short paragraphs per question, or to the stated word/character limit.
- Story-driven, mapped to the specific JD language.
- If a question touches a real documented gap, say so plainly in the
  answer rather than omitting it or implying more than the KB supports.
